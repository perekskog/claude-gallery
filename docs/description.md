# Requirements: Photo galleries (contact-sheet & photo-timeline)

## Background

Two standalone "skills" (code packages) that generate self-contained,
dependency-free HTML pages for browsing a folder of photos. They live in
the project folder as `contact-sheet-skill/` and `photo-timeline-skill/`,
each with `SKILL.md` (documentation + trigger description),
`scripts/generate_*.py` (Python generator), and `assets/template*.html`
(the template the script fills in).

Filename convention for the current dataset: `Pe_YYMMDD_TaO_593_IMG_NNNN.jpg`
(e.g. `Pe_260621_TaO_593_IMG_7444.jpg` = 2026-06-21).

## Shared principles (apply to both skills)

- **A single HTML file, no external dependencies.** Generated by the
  Python script, but the file itself runs entirely standalone in the
  browser (must live in the same folder as the photos, since they're
  referenced by relative path).
- **The same press-and-drag gesture everywhere**, built on Pointer Events
  (`pointerdown`/`pointermove`/`pointerup`/`pointercancel`) — not separate
  touch/mouse listeners — so mouse, touch, and pen all behave identically.
- **Simulated portrait viewport.** The whole page is confined to a
  portrait-shaped rectangle (`PHONE_ASPECT = 9/16`), contain-fit and
  centered within the actual browser window. Rationale: the source photos
  are portrait shots from a phone; on a wide desktop screen, full width
  would otherwise surround every magnified photo with black bars. `9/16`
  (rather than a phone's raw screen ratio of ~9:19.5) was chosen because
  the address bar/toolbar in mobile browsers crops the actually-visible
  area down to something closer to 9:16.
- **Mobile Safari fix.** Size is set from `window.visualViewport` (with a
  fallback to `innerWidth`/`innerHeight`), not CSS `100vh`, because Mobile
  Safari's `100vh` measures the page as if the address bar were hidden —
  otherwise content gets clipped at the bottom. Re-run on `resize`,
  `orientationchange`, and `visualViewport`'s own `resize` event.
- **Onboarding hint (`#hint`).** Real user feedback showed people didn't
  realize the galleries could be browsed. After two rounds of redesign
  (first: a small pill at the edge — missed; second: a banner hanging from
  the top — still missed) it landed on:
  - Centered on top of the photo (`position: fixed; top: 50%; left: 50%;
    transform: translate(-50%, -50%)`).
  - Solid black background + thin white border + shadow — deliberately
    not translucent/pill-shaped, so it reads clearly regardless of which
    photo is behind it.
  - Only dismisses once the user has actually switched to a different
    photo than the one shown initially — not just on the first press (a
    press that doesn't move, or lands outside a thumbnail, doesn't teach
    anything). A 5-second timeout as a fallback if no one interacts at
    all.
  - This principle (centered, solid, dismiss-on-actual-change) should be
    reused if a third layer/skill is ever added.

## Skill 1: `contact-sheet-skill`

Purpose: show all photos in a folder at once, in shuffled order
(re-shuffled on every page load), with the ability to magnify one photo at
a time via press-and-drag.

CLI: `python generate_contact_sheet.py <photo-folder> [-o OUTPUT] [-t TITLE]
[-l grid|border]`. Default output: `contact-sheet.html` (grid) or
`contact-sheet-border.html` (border), in the photo folder. Scans: `.jpg
.jpeg .png .gif .webp .bmp .tif .tiff .heic`.

### "grid" layout (default)

- All photos in a CSS grid; the column/row count is computed to maximize
  thumbnail size without scrolling (search over columns 1..N, score =
  `min(cellW, cellH)`).
- The grid is what's shown by default — no starting photo is preselected
  (tested and deliberately reverted: a preselected photo in the overlay
  hid the grid entirely and made the hint text incomprehensible).
- Press-and-drag: a fullscreen overlay shows a magnified photo under the
  pointer while held down; release hides the overlay and shows the grid
  again.
- Hint text: "Press & drag a photo to preview it". Dismissed on the first
  successful preview (`showAt()` succeeds the first time, since nothing is
  shown initially).

### "border" layout

- Thumbnails line the edges of the screen (top/right/bottom/left strips)
  around a central, always-visible viewer.
- Adaptive number of active sides (`chooseActiveSides(W, H, n)`): grows
  from right-only → right+left → right+left+top → all four, but only when
  each active side can actually get at least `MIN_PER_SIDE` photos (now
  set to 5, after iterative tuning based on user testing: 2 was too low,
  so was 3 — 9 photos should still show on the right edge alone). The
  computation works by actually solving each candidate configuration
  (`solveFrame`), not a static formula, since the distribution depends on
  the screen's proportions (top/bottom get width `W`, left/right get
  whatever height remains).
- Thumbnail size (strip width `s`) is capped at ~16% of the screen's
  shorter side (`maxS`/`capMaxS` in `layoutFrame()`/`solveFrame()`),
  otherwise thumbnails would balloon toward half the screen when few
  photos left plenty of room, squeezing the viewer.
- The starting photo is shown directly in the viewer (`order[0]`), and the
  surrounding thumbnails stay visible at all times (they're never
  hidden), so release just leaves the last-viewed photo in place instead
  of hiding anything.
- Hint text: "Press & drag the border to browse". Only dismisses once the
  viewer has actually switched to a different photo than the starting one
  (tracked via a dedicated `currentViewerSrc` variable, not the DOM
  attribute, for reliability).

## Skill 2: `photo-timeline-skill`

Purpose: browse a photo set chronologically based on the capture date
extracted from the filename — the opposite of contact-sheet's shuffled
order.

CLI: `python generate_timeline.py <photo-folder> [-o OUTPUT] [-t TITLE]`.
Default output: `timeline.html` in the photo folder (in the current
project, manually renamed to `index.html` by the user, likely to serve the
folder over HTTP).

### Date parsing (`parse_date_from_filename`)

Tried in order, most specific first:

1. ISO `YYYY-MM-DD`.
2. 8 consecutive digits read as `YYYYMMDD`.
3. 6 consecutive digits read as `YYMMDD` (year assumed 19xx/20xx: `yy < 70`
   → 20xx) — covers the `Pe_260621_...` convention.

If no pattern matches: falls back to the file's modification time, counted
and reported in the script's output.

### Layout

- Chronological (ascending) order — not shuffled, unlike contact-sheet.
- Each photo is a dot on a vertical line along the right edge, positioned
  proportionally between the earliest (top) and latest (bottom) date — so
  clusters of photos from the same day end up visually close together,
  and gaps in time show up as gaps.
- Collision handling: a monotonic minimum-distance algorithm (forward and
  backward passes) spreads out dots that would otherwise land exactly on
  top of each other (same day), while preserving chronological order and
  relative position as much as space allows.
- Large viewer on the left, with a date badge (pill-shaped, semi-
  transparent + blur — deliberately subtle, unlike the onboarding hint) at
  the bottom. If a photo has a note, it's shown as a wider caption badge
  above the date badge.
- Interaction: nearest-dot-in-Y rather than exact hit detection (the dots
  are small on purpose), so dragging works smoothly anywhere along the
  strip. Listeners are attached to the `#timeline` element (just the thin
  strip), not the whole page.
- Hint text: "Drag the timeline on the right to browse by date". Only
  dismisses once `setActive()` actually changes the index away from the
  starting index 0 — not on a mere press.

### Notes (`photo-notes.json`)

- Sidecar file in the photo folder: flat JSON `{filename: note}`.
  Created/synced on every run — only adds new keys, never overwrites or
  removes existing ones (so hand-written notes survive a re-run even if
  photos are temporarily missing).
- Baked into the HTML at generation time (so the page still works fully
  offline/standalone), but also fetched live via
  `fetch('photo-notes.json')` on every page load, overwriting the baked-in
  values if they've changed — so an edit + reload is enough, no need to
  re-run the script just to update the text.
  - Known caveat: `fetch()` of a sibling file under `file://` is blocked
    by Chrome by default (Firefox allows it). Fallback: baked-in values
    are shown anyway. For guaranteed live updates regardless of browser:
    serve the folder via a simple local server
    (`python3 -m http.server`).

## Packaging / installing as real skills

Skills are developed in the project folder (editable source), but must be
packaged and saved separately to show up as real, invocable skills
(`.skill` zip via skill-creator's `package_skill.py`, presented via the
"Save skill" button). Editing the project folder's files does not
automatically update an already-installed skill.

- `photo-timeline` was packaged and installed early in the process.
- `contact-sheet` hasn't been reinstalled since, despite several
  subsequent changes (border layout, portrait viewport, adaptive sides,
  onboarding hint). Likely out of date compared to the project folder's
  source.
- The user wants to redo the installation for both skills at some point,
  not right now — nothing to do here yet.
